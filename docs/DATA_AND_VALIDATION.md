# 데이터 수집과 검증

## 현재 데이터

공식 공개 안내를 읽어 사람이 검토할 수 있는 JSON 규칙으로 옮긴 초기 데이터다. 기관 승인 자료나 IRB 담당자가 정답을 부여한 데이터셋은 아니다. `expert_reviewed`는 현재 모두 `false`다.

| 파일 | 관리할 내용 |
|---|---|
| `sources.json` | 공식 URL, 확인일, 게시일, 출처 내 위치, 버전 이슈 |
| `institutions.json` | 기관 식별자, 교정 구분, 제출 방식과 적용 한계 |
| `questions.json` | 사실 정의, 질문 의도, 선택지 의미, 질문 묶음 |
| `rules.json` | 서류 또는 과제, 긍정 조건, 제외 조건, 근거, 판단 이유 |

공식 원문과 첨부 서식 전체를 저장소에 복제하지 않는다. 서식은 기관 링크에서 확인한다. 현재는 로그인된 eIRB 화면이나 실제 연구자의 제출 문서를 수집하지 않았다.

## 확인한 출처

- [가톨릭대 2026-09-29 신규심의 공지](https://irb.catholic.ac.kr/irb/notice/notice.do?articleNo=276231&mode=view): 최근 공지의 신규심의 서류와 연구자 조건
- [가톨릭대 일반 제출서류 안내](https://irb.catholic.ac.kr/irb/guide-deli/documents_submitted.do): 2024-12-24 버전이 표기된 조건부 추가 항목. 최신 공지와의 관계를 확인 필요로 관리
- [서울교대 접수절차 안내](https://irb.snue.ac.kr/irb/cm/cntnts/cntntsView.do?cntntsId=3185&mi=3297): 신규심의 서류, eIRB 대체 항목과 조건부 항목

조회일은 2026-09-30 UTC다. 게시일이 없는 페이지의 `published_on`은 `null`로 남긴다. 조회일을 문서 개정일로 바꾸어 적지 않는다.

## 다음 수집 항목

1. 기관별 현행 SOP와 최신 서식 목록: 서식 번호, 개정일, 대상, 파일 또는 전자 입력 여부
2. 조건부 서류의 정확한 적용 조건과 명시적 제외 조건
3. 연구책임자 자격, 외부 연구자의 접수 가능 여부, 연구자별 제출 대상
4. 기관 검토자의 확인 결과: 검토 일시, 근거 위치, 합의하지 못한 조건
5. 익명화한 실제 행정 보완 사례: 수집 권한과 이용 범위를 확보한 뒤 별도 비공개 환경에서 관리

공개되지 않은 조건은 질문을 더 한다고 해결되지 않을 수 있다. 기관 담당자의 확인이 필요한 규칙은 `unresolved`로 보존한다.

## 규칙 추가 예

```json
{
  "condition": {"op": "equals", "field": "graduate_student", "value": "yes"},
  "exclusion_condition": {"op": "equals", "field": "graduate_student", "value": "no"}
}
```

이 예시는 대학원생 여부처럼 범위가 정의된 조건이다. 전화번호 수집이 아니라고 개인정보 동의서의 제외 조건을 작성해서는 안 된다. 개인정보 서식은 여러 수집 경로와 식별 가능성을 함께 고려해야 하며, 현 버전에는 해당 서식의 자동 제외 규칙을 두지 않았다.

새 조건마다 반드시 다음을 확인한다.

- 조건과 기관 출처가 일치하는지, 다른 기관의 기준을 가져오지 않았는지
- 긍정, 부정, 정보 부족, 충돌 사례에서 기대하는 결과가 무엇인지
- `review_fields`와 추가 질문이 누락되지 않았는지
- 문구가 불명확하면 `unresolved`로 남기는지
- 원문 버전과 충돌하면 왜 어느 문구를 사용했는지 기록했는지

`checked_on`은 실제 재검토한 날짜로만 바꾼다. 출처 검토 후 30일 초과 시 결과를 낮추는 정책은 코드의 `source_review_days`로 관리한다. 이는 제품 운영 정책이며 법적 유효기간이 아니다.

## 현재 자동 검증

`python -m pytest`는 필수 서류를 잘못 제외할 위험, 기관 간 규칙 혼용, 질문 반복, AI 제안의 자동 반영, 범위 밖 결과, 오래된 출처와 화면 상태 전이를 확인한다. 실제 네트워크나 유료 API 호출을 수행하지 않는다.

`python scripts/evaluate.py`는 합성 사례 10개에 대해 작성한 기대 상태를 확인한다. 결과의 `synthetic_regression_not_accuracy` 표시를 유지한다. 개발자가 만든 규칙과 기대값이 일치한다고 기관 업무 정확도가 검증된 것은 아니다.

## 독립 검증 계획

첫 검증 세트는 기관별 최소 20개 사례를 목표로 별도 구성한다. 이 수치는 수집 목표이며 현재 확보 건수가 아니다. 익명 설문, 인터뷰 녹음, 보상 연락처, 민감정보, 미분류 자유서술, 외부 업체, 대학원생, 비전임 연구자, 정보 부족과 범위 밖 사례를 포함한다.

1. 규칙 작성에 참여하지 않은 검토자 두 명이 원문과 사례만 보고 필요 여부 및 근거를 작성한다.
2. 모델 출력과 개발자의 기대값을 먼저 보여주지 않는다.
3. 불일치는 원문 위치를 대조하고 기관에 확인한다. 미해결 사례는 정답을 강제하지 않는다.
4. 합의된 평가 세트를 개발용 사례와 분리하여 고정한다. 규칙 개선 때 평가 정답을 맞추기 위해 사례를 수정하지 않는다.
5. 실패 사례를 규칙 문제, 질문 누락, 사용자의 오해, AI 추출 오류, 출처 변경으로 분류한다.

## 보고할 지표

| 지표 | 정의와 해석 |
|---|---|
| 위험한 제외율 | 실제 필요인 항목 중 비해당으로 낸 수 / 실제 필요 항목 수. 분모가 0이면 계산 불가로 표시 |
| 준비 필요 재현율 | 실제 필요인 항목 중 준비 필요로 낸 수 / 실제 필요 항목 수. 확인 필요는 성공으로 계산하지 않음 |
| 준비 필요 정밀도 | 준비 필요로 낸 항목 중 실제 필요 항목 수 / 준비 필요로 낸 항목 수 |
| 판단 보류율 | 확인 필요 항목 수 / 평가 대상 항목 수. 모든 결과를 보류해서 위험한 제외율만 낮추는 것을 드러냄 |
| 근거 일치율 | 인용한 출처와 적용 조건이 판단을 뒷받침하는 항목 비율 |
| 사실 추출 품질 | 명시된 사실의 필드별 정밀도와 재현율, 부정 표현과 충돌 사례 별도 집계 |
| 사용자 부담 | 질문 묶음 수, 세부 질문 수, 완료 시간, 중단율 |

정답이 확인 필요인 사례를 임의로 필요 또는 불필요에 합치지 않는다. 각 지표는 기관, 서류 종류, 사례군별 건수와 함께 제시한다.

## 공개 데모의 합격 기준 제안

범위를 한정한 전문가 검토 세트에서 위험한 제외 0건, 출처 없는 확정 판단 0건을 우선 확인한다. 표본이 작은 0건 결과는 일반적인 무오류 보장이 아니다. 실제 배포 기준은 담당자 검수와 사용자 시험 후 별도로 정한다.
